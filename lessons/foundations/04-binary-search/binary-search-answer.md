## เมื่อโจทย์ถามหา "ค่าที่ดีที่สุด"

โจทย์หลายข้อหน้าตาแบบนี้: "เวลาน้อยที่สุดที่ทำงานเสร็จคือเท่าไร" "ระยะห่างมากที่สุดที่เป็นไปได้คือเท่าไร" ถ้าพยายามสร้างคำตอบที่ดีที่สุดตรง ๆ มักคิดไม่ออก แต่ถ้าเปลี่ยนคำถามเป็น

> "ถ้าคำตอบเป็น $x$ ทำได้ไหม?"

หลายครั้งตอบง่ายกว่ามาก แค่ greedy ไล่ไปรอบเดียวก็รู้แล้ว ส่วนที่เหลือคือหา $x$ ที่ดีที่สุดที่ยัง "ทำได้" ซึ่ง binary search จัดการให้ได้ ถ้าคำตอบของคำถามนี้มีหน้าตาเป็นแบบที่จะเล่าต่อไป

## Monotone predicate

ให้ `ok(x)` เป็นฟังก์ชันที่ตอบ `true` หรือ `false` เราเรียกมันว่า **monotone** ถ้าเรียงค่า $x$ จากน้อยไปมากแล้วผลเป็นแบบนี้

```text
x      =  1  2  3  4  5  6  7  8
ok(x)  =  F  F  F  F  T  T  T  T        อยากได้ T ตัวแรก (x = 5)
```

คือพอเริ่มเป็น `true` แล้วจะ `true` ตลอดไป (หรือกลับกัน `true` ก่อนแล้ว `false` ตลอด) นี่คือแถบสองสีแบบเดียวกับบทที่แล้วเป๊ะ ต่างกันแค่ว่าคราวนี้ "อาเรย์" ไม่ได้มีอยู่จริง เราคำนวณสีของช่องที่ต้องการด้วย `ok(mid)` เอาเอง

ก่อนเขียนโค้ด ถามตัวเองสองข้อเสมอ

1. **ทำไมมันถึง monotone?** เช่น "ถ้ามีเวลา $T$ แล้วทำทัน มีเวลามากกว่า $T$ ก็ต้องทันด้วย" ถ้าอธิบายไม่ได้ binary search อาจให้คำตอบผิดแบบเงียบ ๆ
2. **ตรวจ `ok(x)` ได้เร็วแค่ไหน?** ปกติคือ $O(N)$ ด้วย greedy

## Template

ใช้ invariant คู่หนึ่งที่จำง่ายมาก: **`ok(lo)` เป็นเท็จแน่นอน และ `ok(hi)` เป็นจริงแน่นอน** วนจนสองตัวติดกัน แล้ว `hi` คือค่าแรกที่เป็นจริง

โปรแกรมข้างล่างแก้โจทย์ข้างเคียงนี้: มีเครื่องจักร $N$ เครื่อง เครื่องที่ $i$ ผลิตของได้ 1 ชิ้นทุก ๆ $t_i$ วินาที ทุกเครื่องทำงานพร้อมกัน ต้องการของ $M$ ชิ้น ใช้เวลาน้อยที่สุดกี่วินาที

```cpp
#include <bits/stdc++.h>
using namespace std;

int n;
long long m;
vector<long long> t;

// ภายใน T วินาที ผลิตได้ครบ M ชิ้นไหม   (F F ... F T T ... T)
bool ok(long long T) {
  long long made = 0;
  for (long long ti : t) {
    made += T / ti;
    if (made >= m) return true;        // หยุดทันที กันผลรวมล้น
  }
  return false;
}

int main() {
  ios::sync_with_stdio(false);
  cin.tie(nullptr);
  cin >> n >> m;
  t.resize(n);
  for (long long &v : t) cin >> v;

  long long lo = 0;                                // 0 วินาทีผลิตไม่ได้เลย: ok(lo) เท็จ
  long long hi = *min_element(t.begin(), t.end()) * m;  // เครื่องที่เร็วสุดทำคนเดียวก็ทัน: ok(hi) จริง
  while (hi - lo > 1) {
    long long mid = lo + (hi - lo) / 2;
    if (ok(mid)) hi = mid;
    else lo = mid;
  }
  cout << hi << '\n';                              // ค่าแรกที่ ok เป็นจริง
}
```

ถ้าโจทย์อยากได้ **ค่ามากที่สุดที่ยังทำได้** (ผลเป็น `T T T F F F`) ก็สลับบทบาท: ให้ `ok(lo)` จริง, `ok(hi)` เท็จ, ถ้า `ok(mid)` ให้ `lo = mid` ไม่อย่างนั้น `hi = mid` แล้วตอบ `lo` ลูป `while (hi - lo > 1)` ไม่มีทางวนไม่จบ เพราะ `mid` อยู่ระหว่างสองตัวเสมอ

## ไล่มือหนึ่งรอบ

$t = [2, 3, 7]$ และ $M = 10$ เริ่ม `lo = 0`, `hi = 2 * 10 = 20`

```text
lo=0  hi=20  mid=10  10/2+10/3+10/7 = 5+3+1 =  9  < 10  F  -> lo=10
lo=10 hi=20  mid=15  7+5+2 = 14 >= 10            T  -> hi=15
lo=10 hi=15  mid=12  6+4+1 = 11 >= 10            T  -> hi=12
lo=10 hi=12  mid=11  5+3+1 =  9  < 10            F  -> lo=11
lo=11 hi=12  ติดกันแล้ว  คำตอบ 12
```

ตรวจกลับได้: ใน 12 วินาทีได้ $6 + 4 + 1 = 11$ ชิ้น แต่ใน 11 วินาทีได้แค่ $9$ ชิ้น

## "มากที่สุดของน้อยที่สุด" และ "น้อยที่สุดของมากที่สุด"

ถ้าเห็นวลีพวกนี้ในโจทย์ ให้นึกถึงบทนี้ก่อนเลย

* **maximise the minimum** เช่น วางของให้คู่ที่ใกล้กันที่สุดห่างกันมากที่สุด ให้ถามว่า "ทุกคู่ห่างกันอย่างน้อย $d$ ได้ไหม" ยิ่ง $d$ เล็กยิ่งง่าย ผลเป็น `T T T F F F` หาตัว `T` ตัวสุดท้าย
* **minimise the maximum** เช่น แบ่งงานให้คนที่หนักที่สุดเบาที่สุด ให้ถามว่า "ทุกคนได้ไม่เกิน $S$ ได้ไหม" ยิ่ง $S$ ใหญ่ยิ่งง่าย ผลเป็น `F F F T T T` หาตัว `T` ตัวแรก

ในทั้งสองแบบ `ok` มักเป็น greedy จากซ้ายไปขวา: ทำให้ได้มากที่สุดเท่าที่เงื่อนไขยอม แล้วดูว่าพอไหม

:::problem lp_bsx01_booth_spacing

:::hint ใบ้ Booth Spacing
เรียงจุดก่อน แล้วถามว่า "วาง $K$ บูธให้ทุกคู่ห่างกันอย่างน้อย $d$ ได้ไหม" greedy คือวางบูธแรกที่จุดซ้ายสุดเสมอ แล้วจุดถัดไปที่ห่างจากบูธล่าสุดอย่างน้อย $d$ ก็วางเลย ลองคิดดูว่าทำไมการวางให้ชิดซ้ายที่สุดถึงไม่มีทางแย่กว่า ส่วนขอบของ binary search: $d = 1$ ทำได้เสมอ (จุดไม่ซ้ำกัน) และ $d$ ที่มากกว่าระยะจากจุดซ้ายสุดถึงขวาสุดทำไม่ได้แน่นอน
:::

:::problem lp_bsx02_split_work

:::hint ใบ้ Split the Work
ถามว่า "ให้ทุกช่วงมีผลรวมไม่เกิน $S$ ใช้กี่ช่วง" greedy คือใส่ของลงช่วงปัจจุบันไปเรื่อย ๆ จนกว่าจะเกิน $S$ แล้วค่อยเปิดช่วงใหม่ ถ้าใช้ไม่เกิน $K$ ช่วงก็ทำได้ อย่าลืมว่าถ้ามีชิ้นเดียวที่หนักกว่า $S$ ก็ทำไม่ได้แน่นอน และผลรวมไปได้ถึง $10^{14}$
:::

## เลือก `lo` กับ `hi` ยังไง

ไม่ต้องเป๊ะ ขอแค่ **ถูก** คือ `ok(lo)` ต้องผิดจริง และ `ok(hi)` ต้องถูกจริง (หรือกลับกันในแบบหาค่ามากสุด) ช่วงใหญ่เกินไปหน่อยก็เสียแค่รอบสองรอบ เพราะ $\log_2 10^{18} \approx 60$ เท่านั้น

* หาจากโจทย์ว่าคำตอบน้อยสุดและมากสุดเป็นไปได้เท่าไร เช่น ผลรวมทั้งหมด, ค่ามากสุดของข้อมูล, หรือ "ให้เครื่องที่เร็วที่สุดทำคนเดียว"
* ถ้าไม่แน่ใจว่า `ok(lo)` ผิดจริงไหม ก็ขยับ `lo` ออกไปอีกหนึ่ง (เช่น `lo = 0` หรือ `lo = -1`) ค่าที่ไม่มีวันเป็นคำตอบเอามาเป็นขอบได้ เพราะ template ไม่เคยเรียก `ok(lo)` หรือ `ok(hi)` เลย
* `hi` ต้องไม่ใหญ่จน `ok(mid)` คำนวณล้น ข้อนี้พาไปหัวข้อถัดไป

## ระวังล้นใน `ok`

`ok` มักบวกหรือคูณค่าที่ขึ้นกับ `mid` ซึ่งใหญ่ได้ถึงขอบบนของช่วง ในตัวอย่างเครื่องจักร ถ้าขี้เกียจคิดแล้วตั้ง `hi = 1e18` (ซึ่งก็ยังเป็นขอบที่ถูก) `mid` ก็จะใหญ่ระดับ $10^{17}$ ถ้ามีเครื่อง $10^5$ เครื่องที่ $t_i = 1$ ผลรวม `made` จะไปถึง $10^{22}$ ล้น `long long` แน่นอน ที่ template ไม่ล้นเพราะ **หยุดทันทีที่รู้คำตอบ** (`made >= m`)

ท่าที่ใช้บ่อย

* บวกไปเรื่อย ๆ: หยุดทันทีที่ถึงเป้า
* คูณไปเรื่อย ๆ: ก่อนจะคูณ `r *= x` ให้เช็ก `r > limit / x` ก่อน ถ้าจริงแปลว่าผลคูณจะเกิน `limit` แน่ ๆ ให้หยุดได้เลย การหารไม่มีวันล้น

:::note ทำไมถึงต้องสนใจเรื่องนี้มาก
grader ของเรา compile ด้วย `-fsanitize=signed-integer-overflow` ถ้าจำนวนเต็มมีเครื่องหมายล้นแม้แต่ครั้งเดียว โปรแกรมจะถูกหยุดและได้ Runtime Error ทันที ต่อให้คำตอบสุดท้ายจะบังเอิญถูกก็ตาม
:::

:::problem lp_bsx03_kth_root

:::hint ใบ้ K-th Root
`ok(x)` คือ $x^k \leq n$ ซึ่งเป็น `T T T F F F` คำตอบอย่างน้อย $1$ เสมอ และเพราะ $k \geq 2$ คำตอบไม่เกิน $10^9$ คูณ $x$ ทีละรอบ $k$ รอบ แต่เช็กก่อนคูณทุกครั้งว่าจะเกิน $n$ หรือยัง ถ้าเกินแล้วก็ตอบเท็จได้เลย และอย่าใช้ `pow` หรือ `sqrt` ของทศนิยม เพราะความละเอียดของ `double` มีแค่ประมาณ $15$ หลัก
:::

## จำนวนจริงหรือจำนวนเต็ม

บางโจทย์คำตอบเป็นจำนวนจริง (เช่น "เวลาน้อยที่สุดเป็นวินาที ตอบทศนิยม 6 ตำแหน่ง") แบบนั้นใช้ `double` ได้ แต่ **อย่าวนด้วยเงื่อนไข `hi - lo > 1e-9`** เพราะถ้าค่าใหญ่ ทศนิยมอาจละเอียดไม่ถึงแล้วลูปไม่จบ ให้วนจำนวนรอบตายตัวแทน

```cpp
double lo = 0, hi = 1e9;               // ok(lo) เท็จ, ok(hi) จริง
for (int it = 0; it < 100; it++) {     // ทุกรอบช่วงแคบลงครึ่งหนึ่ง 100 รอบพอเสมอ
  double mid = (lo + hi) / 2;
  if (okReal(mid)) hi = mid;
  else lo = mid;
}
printf("%.6f\n", hi);
```

แต่ถ้าโจทย์ให้ข้อมูลเป็นจำนวนเต็มและคำตอบเป็นจำนวนเต็ม **ใช้จำนวนเต็มเสมอ** มันตรงเป๊ะ ไม่มีปัญหาปัดเศษ และรู้ชัดว่าลูปจบเมื่อไร ถ้าคำตอบต้องการทศนิยมแค่ไม่กี่ตำแหน่ง บางทีก็คูณทุกอย่างด้วย $10^k$ แล้วคิดเป็นจำนวนเต็มได้เหมือนกัน

## ความซับซ้อน

ถ้าช่วงคำตอบกว้าง $R$ และ `ok` ใช้เวลา $C$ ทั้งหมดเป็น $O(C \log R)$ เช่น `ok` เป็น $O(N)$ และคำตอบอยู่ในช่วง $10^{18}$ ก็คือประมาณ $60N$ ครั้ง

เทียบกับการไล่ลองคำตอบทีละค่า $x = 1, 2, 3, \ldots$ ที่ใช้ $O(C \cdot R)$ ถ้า $R$ เป็น $10^9$ ก็ไม่มีทางทัน ความต่างระหว่าง $R$ กับ $\log R$ นี่แหละคือทั้งหมดของบทนี้

:::warning จุดที่พลาดบ่อย
* **`ok` ไม่ monotone** เช่นโจทย์ที่ "ยิ่งมากยิ่งดี" จริงแค่บางช่วง binary search จะหยุดที่ไหนสักแห่งแบบผิด ๆ โดยไม่บอก ให้พิสูจน์ (หรืออย่างน้อยอธิบายให้ตัวเองฟัง) ก่อน
* **ขอบผิด** ถ้า `ok(hi)` ไม่ได้เป็นจริงอย่างที่คิด template จะตอบ `hi` ที่ไม่ใช่คำตอบ ลองเช็กว่าคำตอบที่แย่ที่สุดที่เป็นไปได้อยู่ในช่วงเสมอ
* **สลับทิศ** หาค่าน้อยสุดที่ทำได้ ตอบ `hi`, หาค่ามากสุดที่ทำได้ ตอบ `lo` เขียนคอมเมนต์ไว้ข้าง `lo` และ `hi` ว่าฝั่งไหนจริงฝั่งไหนเท็จ จะไม่สับสน
* **ล้นใน `ok` หรือใน `mid`** ใช้ `long long`, ใช้ `lo + (hi - lo) / 2`, และหยุดบวกหรือคูณทันทีที่เกินเป้า
* **ลืมเรียงข้อมูล** greedy ที่ใช้ใน `ok` หลายแบบต้องการข้อมูลที่เรียงแล้ว (แต่บางโจทย์ห้ามเรียง เช่นต้องแบ่งเป็นช่วงติดกันตามลำดับเดิม อ่านโจทย์ดี ๆ)
:::

## สรุปสั้น ๆ

* เปลี่ยน "หาค่าที่ดีที่สุด" เป็น "ค่านี้ทำได้ไหม" แล้วเช็กว่าคำตอบเป็น `F F F T T T` (หรือกลับกัน)
* template: `ok(lo)` เท็จ, `ok(hi)` จริง, วน `while (hi - lo > 1)` แล้วตอบ `hi`
* maximise the minimum / minimise the maximum = binary search คำตอบ + greedy ตรวจ
* เลือกขอบให้ถูกก่อน ไม่ต้องแคบ $60$ รอบก็ครอบคลุม $10^{18}$ แล้ว
* ใน `ok` ให้หยุดทันทีที่รู้คำตอบ และเช็ก `r > limit / x` ก่อนคูณ จะไม่ล้น
* คำตอบเป็นจำนวนเต็มใช้จำนวนเต็ม ถ้าจำเป็นต้องใช้ `double` ให้วนรอบตายตัว
